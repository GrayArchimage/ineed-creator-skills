# 从本地制作到平台聊天

创作者只需描述目标、确认必要选择、上传 ZIP、粘贴发布说明和测试预览。工程分析、字段汇总、版本与文件校验由 AI 完成，不让创作者抄代码或猜平台参数。

## 前端与后端的分界

| 能力 | 创作者的游戏/网页（前端） | 平台服务（后端与可信界面） | 双方接洽内容 |
|---|---|---|---|
| 账号和用户名 | 放入口、显示昵称、账号变化时清理旧数据 | 认证、会话、按需登录、账号资料 | 游客范围、何时登录、取消行为 |
| 随机匹配/联机 | 本地可联机的玩法、RPC、同步与状态转移、胜负和断线画面 | 匹配隔离、信令、短时 TURN；SDK 安装 WebRTC peer | 模式、人数、build、开局/退出规则 |
| 商品 | 按钮、使用时机、可信成功后的玩法效果 | 商品配置、价格、确认付款、订单、权益、库存与消费校验 | productKey、价格/类型、发放量、实际消费事件 |
| 排行榜 | 真实分数/耗时、开局 ID、冻结结算、榜单界面 | 配置、账号归属、幂等记录、个人最佳、排序/分页 | boardKey、公式、范围、排序、提交时机 |
| 广告 | 合适入口、预留位置、暂停恢复、成功后的奖励效果 | 供应商展示与关闭、可信完成校验和奖励凭据 | 展示/激励、位置、动作和奖励 |
| 存档 | 保存哪些玩法字段、何时保存、版本迁移、冲突 UI | 账号隔离、大小限制、版本校验和存储 | schemaVersion、事件、游客/账号规则 |

游戏调用公开 SDK，不持有数据库密码、平台后台凭据或供应商密钥。平台只能配置已实现的玩法入口，不能仅凭聊天创造缺失的游戏动作。P2P 房主权威不能充当支付校验或服务端反作弊。接口参数、返回、错误按[接口手册](api.md)；能力不支持时明确返回，不让 AI 猜接口。

### 两边独立交付，避免只在开发环境可用

创作者阶段只能依赖公开 Skill、SDK、自己的源码与需求：交付运行 ZIP + 已填写说明，可另附源码 ZIP。冻结文件并计算 SHA256 后，平台阶段只用收到的 ZIP 和说明接入配置、检查 SDK 绑定和预览；若发现玩法缺口，应反馈具体脚本/事件要求给创作者重新导出，不直接用平台私有知识掩盖缺口。

每项能力在说明中标注“代码已实现 / 平台待配置 / 模拟通过 / 真实服务已测 / 尚未测试”。同一作品升级保留作品 ID 和已发布版本，新增待审核版本；平台配置回显与包里的 key/build 必须一致。支付/排行榜尚未有业务规则时可交付 SDK 和隔离测试，但不编造商品、价格、榜单或实测通过结论。

## 先弄清用户要做什么

先读已有工程和本轮需求，保留原设计；询问无法从资料确定、会影响实现的一个关键问题。可用短选项，不强制长问卷。

- 作品目的、核心操作、PC/手机、网页/Godot；有源码还是只有导出包。
- 单机或联机；联机选择随机匹配、联机大厅、邀请的一项或多项，人数、对局开始/结束、断线后的处理。
- 哪些动作需要账号；收费/广告卖的到底是什么、何时使用、永久还是按次、价格/奖励、是否允许广告替代；记录/排行的实际规则。
- 对已上线作品，哪些必须保留、哪些明确允许改。问“是什么配置”只查询，不修改。

只为选中的能力继续收集细节。未选择不等于默认开启；缺失关键规则记“待确认”，不能编造默认价格、奖励、永久权益或联机模式。AI 可以提出建议，但建议不能冒充用户决定。

## 本地制作与检查

按工程、引擎和选定能力的 Skill 制作；保留一份与代码同步的需求记录（已确认 / 待确认 / 建议 / 冲突）。每项能力都记录实际入口、完成后行为、取消或失败行为、平台标识及其来源。

本地检查静态包、相对资源路径、PC/手机布局、加载、真实游戏入口及失败分支。需要平台服务而本地无法验证时明确标记“待平台预览测试”；mock 不得视为购买、发奖或联机真实完成。未获可信成功不能推进付费或激励动作。

本地交付 ZIP 与简短发布说明；技术清单由 AI 保留为附件。ZIP 文件名和 SHA256 由 AI 计算，SDK/协议/兼容版本从工程读取或按项目版本生成，不要求普通创作者手填。

## 最后必须生成一段可粘贴说明

把下面模板填成当前作品的真实信息，放在一个 text 代码块中，建议同时保存为 `creator-handoff.txt`。只保留选中能力的行；不要输出一堆空字段让用户继续整理。缺项集中为短的“待确认”，不得用示例内容填满。

```text
请根据下面已确认需求整理本作品草稿，并回显配置和还缺的信息；先供我预览测试、审核后发布。
作品：<实际名称>；本次包：<实际 ZIP 文件名>；版本：<实际版本>
我想做：<玩法/用途的一两句话>。
本次要接入：<用户选择的平台能力>；请保留：<原设计和既有线上规则>。
登录：<游客是否可进入，以及哪些操作才登录>。
联机：<随机匹配/大厅/邀请的实际选择>；<人数>；兼容版本 <实际 build>；<断线规则>。
商品：<逐项写名称、用途、价格单位、永久或按次、真实使用/消费时机、广告替代选择和失败不能放行>。
广告：<展示/激励、用户认可的位置与触发条件、关闭/无填充行为；如激励则写奖励>。
进度/排行：<实际保存和上报规则>。
本地已完成：<真实实现及测试结果>。
需要平台处理：<待配置、绑定、启用或预览验证的具体事项>。
待确认：<仅列确实缺失的决定；没有则删掉此行>。
测试入口：<从哪个界面点击什么，预期结果>。
包校验：SHA256 <AI 计算的实际值>。
```

模板不是固定 API，也不是后台已保存的证明。平台未返回的 productKey、广告位 key、boardKey 不得自行冒充已绑定；可用项目内部稳定别名并标明待绑定。密钥、密码、令牌和私钥绝不放进聊天说明或 ZIP。

## 明确告诉创作者下一步

交付时用一句直接提示：**“上传这个 ZIP 后，把下面整段发布说明复制到该作品的平台聊天中。”** 不要只把说明放在文件中而忘记提醒。

随后由平台聊天整理并回显当前草稿。AI/创作者对照确认价格、权益、联机模式、登录时机和接入状态；平台只改配置不代表游戏代码已经接好。需要代码中的标识或事件调整时，用平台真实回显更新源码、重新导出并生成新的说明，旧包说明不能套给新包。

最后在平台预览测试真实登录、成功/失败支付、广告、存档、排行或双端联机，再交审核。说明“本地验证 / 平台待配置 / 平台已验证 / 已发布”各自实际状态；不要把整理草稿、上传或模拟成功说成已经公开上线。

## 双角色实测与反馈

需要模拟完整交付时，先冻结创作者 ZIP、原始说明和 SHA256，再由独立平台角色接包。平台先依据这两份输入判断；发现缺失时，返回具体入口、预期/实际、错误码和需要补的最小信息。创作者修好后重新打包，不让平台悄悄依赖创作者未上传的工作目录。

创作者 AI 记录实际操作耗时、需要的手动步骤、首个失败与恢复结果，并给平台反馈：公开文档是否一致、SDK 接入是否直接、错误是否可理解、说明是否能一次粘贴。平台 AI 记录包/归属/build 检测、配置回显、失败兜底、真实双端运行和未验证项；指标没有测量时写未测，不给主观数字。共享技术附件由 AI 维护，普通用户仍只上传包和粘贴说明。

联机失败时先给平台作品/版本、入口、发生时间、设备/浏览器及可见错误码。同账号双端并不等于异常；仅在匹配冲突时由平台询问顶替。不要要求创作者粘贴令牌、SDP、ICE、房间码或清缓存作为默认修复。

新增游戏广告按[展示广告事件](display-ads.md)交接。不要把展示广告当成购买成功或激励完成。游戏内保留创作者设计，调试原因和审核说明放在交接附件，不堆到玩家界面。
